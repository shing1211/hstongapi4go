1. CI-1 — gofmt gate failed, skipping four steps
------------------------------------------------

internal/push/fanout_test.go
internal/push/normalizer_test.go
test/integration/push_integration_test.go

All three had misaligned struct fields and one-line method bodies. The failing
step was "gofmt check", which runs before vet, test, race, and money-check, so
none of those had run on main since E15.

Method note: plain `gofmt -l .` is useless on this Windows host. The working
tree is CRLF and gofmt normalises to LF, so it lists every file. A local
golangci-lint run appeared to report ~130 gofmt findings for the same reason.
The real signal required a core.autocrlf=false view:

  git -c core.autocrlf=false -c core.eol=lf archive <tree> | tar -x -C tmp
  cd tmp && gofmt -l . | grep -v '^gen/'

That is the view the Linux runner sees. See item 6, which removes the problem.

3. CI-3 — security job never ran
--------------------------------

Two separate causes.

Wrong module. The workflow installed honnef.co/go/tools/cmd/gosec. That is
staticcheck's module; the path does not exist, so the step failed and
govulncheck was never reached. Corrected to
github.com/securego/gosec/v2/cmd/gosec@v2.22.10, and govulncheck pinned to
v1.1.4, so a scanner result is reproducible instead of drifting with @latest.

gosec: 23 findings outside gen/, plus 68 inside generated protobuf. Generated
code is excluded with -exclude-generated, which keys off the standard
"Code generated by ... DO NOT EDIT." header rather than a path list, matching
how golangci-lint already treats gen/. Every rule stays enabled and each
suppression is an inline "#nosec RULE -- reason" at the call site, documented
in .gosec.yml.

One real defect fixed: Quantity.ValidateLot converted a uint64 lot to int64
with no range check, so a lot above MaxInt64 wrapped negative and produced a
wrong modulus. Now rejected. The other 22 were reviewed and are false
positives: fixed-width wire encode/decode in the frame codec, where ReadFrame
range-checks BodyLen for negative and above MaxBodyLen before allocating; the
published HStong AES key, which is public reference data; SHA1WithRSA
verification, which the Gateway wire protocol mandates; retry and reconnect
jitter; a hardcoded argv in a developer script; and example logging.

govulncheck: 14 findings, all in the Go standard library at go1.26.1 and all
fixed in go1.26.6 — net/url, crypto/tls, net/http, encoding/asn1 and others,
reachable from this module's own call graph. Added `toolchain go1.26.6` to
go.mod. That pins the toolchain used to build and scan without raising the
`go 1.26` language floor for consumers, and GOTOOLCHAIN=auto fetches it. Now
reports no vulnerabilities.


4. CI-4 — GoReleaser config was never valid
--------------------------------------------

Two causes.

Install. `go install github.com/goreleaser/goreleaser@latest` resolved a
dependency on golang.org/x/tools@v0.21.0, which does not compile under the
Go 1.26 compiler:

  golang.org/x/tools@v0.21.0/internal/tokeninternal/tokeninternal.go:64:9:
      invalid array length -delta * delta (constant -256 of type int64)

Replaced with goreleaser/goreleaser-action@v6, which installs the published
binary.

Config. .goreleaser.yaml did not parse:

  yaml: line 26: mapping values are not allowed in this context

Line 25-26 had a botched edit merging two list entries:

  files:
    - none/**
      glob: "**/*.go"

Beyond the syntax error, the config was wrong on several counts: it set
`main: .`, but the repository root is a library with no main package; it forced
`tags: [otel]` on every build, contradicting the opt-in design; and its cosign
block referenced a key/OIDC setup the repository does not have, so it would have
failed a real release.

Rewritten to build cmd/hstong-mock-gateway, the only main package, with CGO
disabled and -trimpath; archives, checksums, and SPDX SBOMs; GitHub release
metadata. Signing and attestation were removed rather than left in a state that
cannot succeed.

Verified with a real GoReleaser v2 binary:
  goreleaser check                     exit 0, configuration valid
  goreleaser build --snapshot --clean  exit 0, all six targets built
                                       (darwin/linux/windows x amd64/arm64)


5. CI-5 — two failures that the first one had been hiding
---------------------------------------------------------

With gofmt green, the four jobs that had always been SKIPPED finally ran, and two
of them failed.

proto-verify. The committed gen/ did not match a Linux regeneration, in exactly
one line of one file:

  - //行情占用2000开头      committed
  + // 行情占用2000开头    regenerated

Root cause: buf's comment normalisation differs between CRLF and LF input. The
committed gen/ had been produced on a Windows checkout, from CRLF protos, so it
carried the CRLF-input form. proto/PROVENANCE.md requires the vendored protos to
stay byte-for-byte, so the source was not edited.

Reproduced deterministically by running buf generate inside an archived copy of
the committed tree, and confirmed the inverse: generating from the CRLF working
tree reproduced the committed bytes exactly.

Fixed at the root by forcing LF checkouts. .gitattributes now sets eol=lf for
text, Go, proto, Markdown, YAML, Python, and shell files. The committed blobs
were already LF, so the sole content change is that one comment line in
gen/common/constant/NotifyMsgType.pb.go, now the deterministic LF-input form.
proto/ is untouched.

After: buf generate matches gen/ byte-for-byte, 0 mismatches across 17 files.

docs-check. mkdocs build --strict aborted on a warning: the
git-revision-date-localized plugin warns when it detects a shallow git fetch,
and --strict promotes warnings to failures. mkdocs.yml already tries to
disable that plugin in CI with `enabled: !ENV [CI, false]`, but !ENV substitutes
the string "true" when CI is set, which is truthy and leaves the plugin on. The
docs job now checks out with fetch-depth: 0, so the plugin has real history and
does not warn.

Separately, the docs job was missing mkdocs-git-revision-date-localized-plugin
from its pip install, which aborts the build on a config error.


6. Toolchain note

usable as a signal on Windows. This removes the reason the `make fmt-check`

no longer the only way to reproduce the runner's view.

8. Known limitations, not repaired here
---------------------------------------

- The Release workflow only runs `goreleaser check`. It never publishes. Tagging
  v0.1.6 therefore produced a git tag and nothing else; binaries, checksums,
  and SBOMs have never been released. Switching the step to `goreleaser release`
  is a functional change that starts writing to a public repository and needs
  the release credentials settled first, so it was left for a decision rather
  than changed silently.
- GoReleaser builds only cmd/hstong-mock-gateway. The library itself needs no
  binary, so a tag-based release is otherwise sufficient.
- CI does not run go test -race under the otel tag, and govulncheck runs against
  the default build only.
